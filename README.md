# RAG 知识库问答（rag-knowledge-qa）

基于 **检索增强生成（RAG）** 的企业知识库问答系统：上传 PDF，即可用自然语言提问，
回答**只基于文档内容**并带**可点击的引用溯源**，检索不到就明确拒答，不编造。

技术栈：FastAPI + Qdrant + PostgreSQL + Redis + BGE（embedding/reranker）+ 原生 JS 前端。

![界面](docs/ui.png)

> 截图里的三个能力：中间是流式回答与 `[n]` 引用标注；右侧是命中的原文片段与相关度分数；
> 左侧是知识库文档管理与三种检索模式切换（黄色气泡为"知识库中没有该内容"的拒答）。

---

## 功能

- **PDF 问答**：上传 → 后台解析/清洗/切分/向量化入库，状态实时可见
- **混合检索**：BM25（jieba 中文分词）+ 向量双路召回，RRF 融合名次，再用交叉编码器精排
- **流式输出**：SSE 打字机效果，来源先于正文到达
- **引用溯源**：回答中的 `[1][2]` 可点击，联动高亮右侧对应原文；编号越界（只有 5 条
  来源却写 `[6]`）由后端/前端兜底剥掉，代码块里的 `chunks[0]` 不会误伤
- **多轮对话**：前端带最近 3 轮历史，后端先做查询改写（指代消解）再检索——
  「它需要哪些依赖」→「运行 RAG agent 需要哪些依赖」；「我不明白」会自动换说法重讲
- **拒答机制**：材料不足时按"是否属于本知识库主题"分三种处理——
  主题内但没写 → 拒答（内部资料不能用外部常识替代）；
  问某个组织的内部事务 → 拒答；完全无关的通用问题 → 用模型自身知识回答，
  并在答案开头标注「（以下不属于知识库内容）」、不标任何引用编号
- **闲聊/身份短路**：`你是谁`、`你好`这类问题不走检索（正则分流，0 成本），
  避免弹出 5 个无关来源误导用户，也省掉一次 embedding+rerank
- **三种检索模式**可切换对比：`vector` / `hybrid` / `hybrid_rerank`
- **评估体系**：检索层命中率 + RAGAS 答案层质量，优化前后全程有数字背书

## 架构

```mermaid
flowchart LR
    A[PDF 上传] --> B[解析 pypdf]
    B --> C[清洗: 去页眉页脚噪声行]
    C --> D[切分 300字/重叠30]
    D --> P[(PostgreSQL chunks<br/>原文 source of truth)]
    P --> E[BGE 向量化]
    E --> F[(Qdrant<br/>向量 + chunk_id)]
    P -. 全量原文 .-> G[BM25 内存索引 jieba]

    Q[用户提问] --> R{检索模式}
    R -->|vector| S[向量检索]
    R -->|hybrid / hybrid_rerank| T[向量 + BM25 双路 top20]
    T --> U[RRF 融合 k=60]
    U --> V{rerank?}
    V -->|是| W[交叉编码器精排 top5<br/>bge-reranker-v2-m3]
    V -->|否| X[top5]
    W --> X
    S --> X
    X --> H[按 chunk_id 回 PG 补原文<br/>BM25 路的已在内存]
    H --> Y{分数低于门槛?}
    Y -->|是| Z[丢弃低分块<br/>材料置空]
    Y -->|否| AA[组装 Prompt: 主题 + 材料 + 问题]
    Z --> AA
    AA --> AB{模型判定}
    AB -->|主题内但材料没写| AC[拒答]
    AB -->|不属于本库的通用问题| AD[通用知识回答<br/>标注"非知识库内容"]
    AB -->|材料够用| AE[带引用回答]
    AD --> AF[SSE: meta → sources → token×N → done]
    AE --> AF
    AC --> AF
```

检索采用工业标准的**两段式架构**：快的海选（向量+BM25 取 top20）→ 准的精排（交叉编码器挑 top5）。

**数据分层**：原文只存 PostgreSQL 一份，Qdrant 里只有向量和一个 `chunk_id`（= chunks 表主键）。
这么切的好处是"向量是派生数据"——换 embedding 模型时原文一个字不动，
跑 `scripts/reindex.py` 重算向量即可，切分结果也没变，所以换模型前后的效果对比是干净的。
反过来（原文只放向量库 payload）时，换模型就得重新解析 PDF、重新切分，
历史结果直接失去可比性；想按文档/页做统计还得全量 scroll。

**为什么门槛前面能"丢材料"却不能"直接拒"**：低分块全是噪声，喂给模型只会干扰；
但"分低"有两种完全不同的原因——库里真没有（该拒），或者这根本不是知识库的问题
（该用模型自己的知识答）。在检索层一刀切拒掉，等于把模型的通用能力阉了。

## 评估

评估集：golden set 29 题（17 可答 / 10 应拒 / 2 应通用答），切分参数 300/30。
分三层量，从便宜到贵：**检索命中率（免费，秒出）→ 拒答边界（约 5 万 token，3 分钟）
→ RAGAS（约 25 万 token，52 分钟）**。顺序不能反：尺子没校准就花钱，最后只能重跑。

**题集怎么来的**：`scripts/gen_evalset.py` 让 LLM 只看着单个 chunk 出题
（手写题会不自觉"照着答案出题"，题干和材料高度重合，检索必中，分数虚高），
再用本地向量检索做一遍免费质检（top1 分 + 是否命中标注页），
人工按质检列筛过后 `--finalize` 固化成 `eval/golden_set.json`。
两个评估脚本都默认读这个文件，所以换题集不用改命令。

> 出题时混用了两种风格：一半题不提术语名（考语义检索），一半题直接点名
> 类名/函数名（考关键词检索）。只用一种会让某一检索路占便宜。

> 标注复核（2026-10-26）：原「DeepAgents是什么」标为有答案，复核语料后发现全文
> 只有 URL 路径、代码与导航链接，没有一句定义，已改判为**应拒答**。
> 这条标注错误是在把拒答规则收紧到"定义类问题必须有显式定义句"之后跑出来的——
> 尺子变严，反而先纠正了尺子自己。

> 题集现状（2026-10-26）：**29 题**——17 道可答（全部带参考答案）+ 10 道应拒答
> （7 主题内缺内容 / 3 组织内部事务）+ 2 道应通用答（与本库无关的
> 通用问题，正确行为是用模型自身知识回答并标注，不是拒答）。
> 当天先后改判了两道标错的题（可答 19→17），两次都是"生成式出题 + 语料缺陷"
> 造成的：一道把"代码里出现过"当成"文档里有定义"，一道的答案正好落在
> pypdf 抽取时丢掉的文字里（见坑 6、坑 9）。

### 第一层：检索命中率（17 道可答题，免费秒出）

同一题集、同一套切分（300/30），只换 embedding 模型：

| 模式 | bge-small-zh-v1.5<br/>512 维 / ONNX fp32 | bge-m3<br/>1024 维 / 多语言 fp16 |
|------|:---:|:---:|
| 纯向量 | 35% / 59% / 0.428 | **59% / 88% / 0.706** |
| 混合(RRF) | 47% / 82% / 0.580 | **71% / 88% / 0.784** |
| 混合+精排 | 47% / 88% / 0.642 | 59% / **94%** / 0.725 |

（依次是 hit@1 / hit@5 / MRR）

**四个结论，按可信度排序：**

1. **换 embedding 是最大的一笔收益，而且三个模式都吃到。** 纯向量 hit@1 35%→59%，
   hit@5 59%→88%；混合 47%→71%；精排 hit@5 88%→94%。
2. **精排的收益随底座变好而边际化。** bge-small 上加精排，MRR +0.062
   （0.580→0.642）；换到 bge-m3 再加精排，hit@1 反而少 2 题、MRR -0.059。
   合理解释是**天花板效应**：底座已经把对的块放进前 5（88%→94% 是精排真赚的部分），
   剩下的排序误差不是"相关性判断"能修的。这也说明"换模型"和"加精排"该按顺序做，
   先换底座、再决定要不要精排——本项目的回答是：留着，因为 hit@5 稳定 +6pp。
3. **17 道题下，1 道题 = 5.9pp，hit@1 差 1~2 题就是噪声。** 所以不要拿 59% vs 71%
   下结论说"精排不如混合"；能站得住的是 hit@5 这条线：59% → 82% → 88%（bge-small）、
   88% → 88% → 94%（bge-m3），两套模型上都不降。
4. **中文提问 × 英文语料的短板补上了。** 换模型后 8 道题排名前移（`检索出来的片段
   存到哪个文件夹`、`怎么和 Claude/VSCode 这类工具连起来` 都从未命中变第 1 位），
   2 道题后移——净 +4 题，不是全胜。

> 精度口径要说清楚：bge-small 走 fastembed/ONNX（fp32），bge-m3 走
> sentence-transformers **fp16**（4GB 显卡放不下两个 fp32 模型，见坑 8）。
> fp16 与 fp32 之间有 ±1 题的排名抖动（实测纯向量 hit@1 53%↔58%），
> 所以**换模型对比必须固定精度**；这里的 24pp 差距远大于抖动幅度。

**无答案题的拦住率：9% / 9% / 0%，基本靠不住。** 精排对"完全无关"的输入会恒定输出
0.500——那是 sigmoid(0)，等于模型在说"没有判断依据"；而"主题内缺内容"这类题
材料沾边，分数能到 0.673，与正例最低 0.506 完全重叠。**任何单一分数阈值都分不开**，
拒答最终靠两层：检索门槛做粗筛（省 token），LLM 按 prompt 判断"材料能否回答"做细判。
这条结论在 10 题基线时就得出过，17 题上又验证了一遍。

**代价也要说清楚**：拦住率 0% 意味着每题都把 5 块材料塞给模型，连该拒答的题也在烧
token；换来的是"不会因为门槛误杀而把能答的题也拒掉"。这是一个明确的取舍，
不是没做优化。

| 指标 | 纯向量 | 混合(RRF) | 混合+精排 |
|------|:-----:|:---------:|:---------:|
| hit@1 | 43% | 43% | **57%** |
| hit@5 | 57% | 71% | **86%** |

且只有 10 题，一道题就能让 hit@1 跳动 14pp。留着是为了说明"尺子怎么变的"。

注意这组数字里混合模式**没有**超过纯向量，而新题集上是反过来的——
原因是新题集有一半点名了类名/函数名（`RecursiveCharacterTextSplitter`、
`backend.upload_files`），BM25 正好吃这类词；旧题全是口语化中文，关键词路等于摆设。

### 第二层：拒答边界（scripts/eval_boundary.py，每题一次生成调用）

检索层只管"块找对没"，答案层只管"答得好不好"，**两条都测不到换生成模型之后
那条"该答 / 该拒"的线有没有移动**。这一层补的就是这个洞。

判据与 API 完全一致（不另立标准）：以「根据现有资料无法回答」开头=拒答，
以「（以下不属于知识库内容）」开头=通用答，其余=作答。

| 版本 | 该答的答了 | 该拒的拒了 | 通用题标对 | 总一致率 |
|------|:---:|:---:|:---:|:---:|
| qwen-plus（首版 prompt） | 16/18 | 8/9 | 2/2 | 90% |
| qwen-plus（补了"代码不算定义"后） | 17/17 | 10/10 | 2/2 | **100%** |

换模型时确实撞到了边界漂移：`qwen-plus-2025-12-01` 把「StateBackend 是干啥用的」
从拒答改成了作答，而且答得**像模像样**——它从 `backend = StateBackend()` 和函数的
docstring 里反推出"这是文件系统后端，用于保存检索到的文档块"。这句话材料里没有，
是它自己拼的。修法是在规则 2(a) 里补一句区分：

> 代码只说明「怎么用」，不说明「是什么」…反推出来的句子读起来很像对的，
> 但那句话是你编的，不是材料说的

同时反向也补了一条（否则会矫枉过正）：问**参数格式 / 写法 / 调用方式**时，
代码示例本身就是答案，看到 `uploads.append((path, content))` 就可以直接回答。
两条一起加，误拒和漏拒同时消失。

> 这一层很便宜（29 题 ≈ 5 万 token，3 分钟），但只有它能在换模型那天救你——
> 上面那两道误拒和一道漏拒，检索指标和 RAGAS 都不会报错。

### 第三层：答案质量（RAGAS，LLM 当裁判）

17 道可答题 × 3 模式，同一份答案生成链路（bge-m3 + `qwen-plus-2025-12-01`），
每题 4 个指标全部算完，样本数均 17，**没有一题因门槛被跳过**：

| 指标 | 纯向量 | 混合(RRF) | 混合+精排 |
|------|:-----:|:---------:|:---------:|
| faithfulness（忠实度/反幻觉） | 0.861 | **0.871** | 0.843 |
| answer_relevancy（切题度） | 0.820 | 0.723 | **0.875** |
| context_precision（检索精度） | 0.809 | 0.789 | **0.862** |
| context_recall（检索召回） | 0.941 | 0.941 | **1.000** |
| 耗时 | 932s | 979s | — |

**最重要的一条：切分/语料都没动，只换了 embedding，"
混合检索在跨语言语料上 recall 反而掉"这个反直觉结论消失了。**

| context_recall | 纯向量 | 混合 | 精排 |
|---|:---:|:---:|:---:|
| bge-small 时期（10 题 + 中文分词语料） | **1.000** | 0.722 | 0.810 |
| bge-m3 时期（17 题 + 改造后语料） | 0.941 | 0.941 | **1.000** |

当初的判断是"BM25 用中文分词去匹配英文原文，等于噪声源，把正确块挤出 top5；
要根治只能换多语言 embedding"。换完再看，**判断成立**：正确块不再被挤掉，
混合模式从 0.722 追回到 0.941，精排直接满分。

三个模式各自的胜负点（这一轮和上一轮不一样，不要照抄旧结论）：

- **精排这次全面领先**：precision 0.862（上一轮它是最低的 0.775）、recall 1.000、
  relevancy 0.875。上一轮"精排偏好代码块、把不相关块排前面"的现象没有复现——
  底座换成 bge-m3 之后候选池质量上来了，精排的排序偏好不再是瓶颈。
  代价是 faithfulness 0.843 最低：它挑出的块更"专业"，模型更愿意顺着写，反而更容易越界。
- **混合模式 relevancy 最低（0.723）**，原因很具体：有 3 道题答成了拒答或答偏，
  而 answer_relevancy 是"拿答案反推问题"，拒答必然 0 分。这不是检索质量问题，
  是**RAGAS 的固有前提**——它假设每题都该被回答。所以看 RAGAS 必须同时看拒答率，
  否则"检索差"和"模型保守"会被混成一个数字。
- **纯向量是中游型选手**：四项都在中间，没有短板也没有亮点。

> 口径：裁判模型 `qwen-plus-2025-12-01`，temperature=0、max_tokens=4096。
> 换裁判 = 换评分标准，**这张表不能和换模型之前的数字直接比**；
> 上表第二行那组旧数字是 bge-small + qwen-plus 时代的，只用来对照"反转消失"这一件事。

<details>
<summary>历史：10 题时期 + bge-small 的 RAGAS 结果（裁判 qwen-plus）</summary>

| 指标 | 纯向量（6 题） | 混合(RRF)（6 题） | 混合+精排（7 题） |
|------|:-----:|:---------:|:---------:|
| faithfulness（忠实度/反幻觉） | 0.855 | 0.858 | **0.927** |
| answer_relevancy（切题度） | 0.890 | 0.901 | **0.920** |
| context_precision（检索精度） | 0.792 | **0.825** | 0.775 |
| context_recall（检索召回） | **1.000** | 0.722 | 0.810 |

**样本数不同是有原因的**：`怎么创建智能体` 在向量/混合下 top1=0.438 低于门槛被系统拒答
（不计分），而精排分数是另一套标度（0.508 > 0.5），所以被作答了——但它的
context_recall=0（中文"智能体"vs 英文 "agent"，正确页根本没检回来），
单这一题把精排的 recall 拉低了约 0.12。**跨模式比平均数要小心，样本集不一致**。

三个模式各自的胜负点很清楚：

- **faithfulness**：精排最高 0.927。交叉编码器挑出来的块更贴题，模型少发挥
- **context_precision**：混合最高 0.825，精排反而略低——精排偏好代码块，
  把"能回答问题但不是最相关"的块排在了前面
- **context_recall**：纯向量最高 1.000，混合掉到 0.722

recall 的这次反转是**真信号**，不是噪声：逐题看，降分集中在
`如何用LangChain做RAG`（1.0→0.0）、`文本切分器是什么`、`文档切好块之后存到哪`（1.0→0.667）。
原因是**中文提问 × 英文语料**——语料通篇是 LangChain 英文文档，BM25 用中文分词后的
关键词几乎能命中每一块，RRF 融合后把原本正确的块挤出 top5。hit@5 看不出来，
因为它的判定是"沾边就算命中"；RAGAS 的 recall 要求"必要材料真的都在"，一挤就没分。

当时的结论是：混合检索不是普适的赢，跨语言场景是"用召回换精度"的赌注，
要根治只能换多语言 embedding。**这条预测后来被验证了**（见上面主表：0.722 → 0.941）。

</details>

## 快速开始

### 0. 前置要求

- Docker Desktop（应用本体和 PostgreSQL / Redis / Qdrant 全在容器里）
- 一个 OpenAI 协议兼容的 LLM API Key（DeepSeek / Qwen / GLM 均可）

## API

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/chat` | 一次性返回完整 JSON（脚本/评估用） |
| POST | `/chat/stream` | SSE 流式返回（前端用），事件序列 `meta → sources → token×N → done` |
| POST | `/documents/upload` | 上传 PDF，后台异步入库 |
| GET | `/documents` | 文档列表与入库状态 |
| GET | `/health` | PG / Redis / Qdrant 三组件健康检查 |

请求体示例（`history` 可选，最多 20 条，前端只传最近 3 轮）：

```json
{
  "question": "它需要哪些依赖",
  "top_k": 5,
  "mode": "hybrid_rerank",
  "history": [
    { "role": "user", "content": "怎么运行RAG agent" },
    { "role": "assistant", "content": "运行步骤：1 装依赖 2 建向量库 3 初始化并 invoke。" }
  ]
}
```

带 `history` 时后端会先做**查询改写**再检索：把「它需要哪些依赖」改写成
「运行 RAG agent 需要哪些依赖」再去检索（改写结果在 `meta.rewritten_query` 里回传）。
改写只影响检索用的查询，生成时传的仍是用户原话——「我不明白」这类困惑信号不会丢。

## 技术选型与理由

| 决策 | 选择 | 为什么 |
|------|------|--------|
| 前端 | 原生 HTML/CSS/JS | 只有一个页面、两个状态变量，React 的组件复用与状态管理都用不上；引构建链只会把启动从 2 条命令变 6 条。省下的复杂度换成了能讲清原理的 SSE 解析、防 XSS 渲染 |
| 流式 | SSE 而非 WebSocket | 单向推送场景，一个不关闭的 HTTP 响应就够，不需要 WS 的连接管理；且用 `fetch` 读流（而非 EventSource）才能带 JSON body |
| 检索 | 混合 + 精排两段式 | 实测（bge-m3，17 题）：hit@1 59% → 71% → 59%，hit@5 88% → 88% → 94%。混合补的是"第一名选对"（hit@1），精排补的是"正确块别掉出前五"（hit@5）。三模式 hit@5 都不降，所以默认开精排 |
| 切分 | 300 字 / 重叠 30 | 消融实验胜出：hit@1 14%→43%，MRR 0.243→0.476（同样 10 题，500/50 对比 300/30） |
| 评估 | 两层而不是 AutoRAG | 10 题 golden set 撑不起网格搜索（会过拟合测试集），借 AutoRAG 的思想（海选用便宜指标、决赛才上 LLM 裁判）而不引框架 |
| Reranker | bge-reranker-v2-m3 | 必须多语言：中文提问 × 英文语料。bge-reranker-base 实测跨语言打分全贴 0.500（sigmoid 零点 = 无判断力），排序等于随机 |

## 踩坑记录（节选）

完整记录见开发笔记，以下是对后来者最有用的几条：

1. **torch 装成 CPU 版**——`torch.cuda.is_available()` 返回 False 时一切推理都在 CPU 硬算；
   同样的 20 对候选，CPU 4s vs GPU 0.42s。装 CUDA 版只需换后缀：`torch==x.y.z+cu132`。
2. **RRF 融合的身份键**——用"原文前 80 字符"做去重键时，跨页重复的代码块会被当成
   同一条，分数重复累加导致排名虚高。改用稳定 id；原文挪进 PG 后直接拿 `chunk_id` 当键。
   改造中又踩了一次：向量路和 BM25 路的键构造方式不一致（一个用 point id、
   另一个用文件名+序号），两路分数合不到一起，混合指标整体下滑 14 个点——
   而纯向量那一路**完全没变**，正是这个对比把问题锁死在融合环节、而不是检索环节。
3. **相关性 ≠ 可回答性**——reranker 只能判断"这段和问题有关"，判断不了"这段能否
   回答问题"。文档通篇讲 LangChain 时，"什么是LangChain"照样拿高分。因此拒答必须
   双保险：分数门槛粗筛 + LLM prompt 细判，实测两层各自独立生效。
4. **切分参数的隐式默认值**——API 上传路径和脚本入库路径用了不同的默认 chunk 参数，
   两条入库路产出不一致。修复方式是把根默认值收口到一处。
5. **静态目录挂载顺序**——`StaticFiles` 挂到 `/` 会成为兜底路由吞掉所有 API，
   必须挂子路径（本项目挂 `/ui`）。
6. **pypdf 抽内联代码会丢字**——PDF 里等宽字体的内联代码是独立文本块，按坐标抽取时
   会被甩到句子后面：
   `Use the RecursiveCharacterTextSplitter to recursively split the documents...`
   抽出来的却是 `Use the to recursively split the documents ... RecursiveCharacterTextSplitter`。
   后果很隐蔽：材料里明明有定义句，模型看到的是残句，按"有没有一句在讲 X 本身"的规则
   判定为没有，于是拒答——而人工看 PDF 原文会觉得"这题明明能答"。
   清洗救不回来（清洗只能删噪声，补不回丢掉的词），要根治得换解析器
   （pdfplumber / pymupdf 能保留文本流顺序）。
7. **评估工具自己也会坏**——生成式题集的质检列一度不可复现：旧代码用
   `recreate_collection` 重建临时集合（新版 qdrant-client 已废弃，行为不保证），
   复算后"19 道可答题全部命中"变成"只命中 7 道"，手工实测确认复算值才对。
   尺子坏了比东西坏了更危险——它会让一份看起来很漂亮的分数完全没有意义。
8. **4GB 显存放不下两个 568M 模型**——bge-m3(fp32 2.1GB) + bge-reranker-v2-m3
   (fp32 2.3GB) 在 RTX 3050 Ti Laptop 上必 OOM。**报错位置是关键线索**：不是
   `predict` 时 batch 太大，而是 `__init__` 里 `.to(device)` 搬权重那一刻就炸，
   说明模型本身装不下，调 `batch_size` 完全无效（白改过一次）。
   解法是 fp16：`model_kwargs={"torch_dtype": torch.float16}` 让权重在
   `from_pretrained` 阶段就是半精度，两个模型各约 1.15GB，实测峰值 2.12GB / 4.00GB，
   精排 20 对 0.22s。注意不能写成"先 fp32 建好再 `.half()`"——那会多要一份
   临时显存（报错里那句 allocate 978MB 就是它）。
   同一台机器上还撞过第二种失败：`OSError: 页面文件太小 (os error 1455)`，
   这是**系统虚拟内存（commit）**不够，跟显存无关。同一天踩了三次，成因各不相同：
   ① 上一轮崩溃残留的 python 进程还占着 2.5GB；② 服务和评估脚本同时各加载一份
   2.3GB 模型；③ 失败的评估进程没退出，继续占着 3GB。教训是**跑评估前先确认
   uvicorn 已停**（两者都要把模型读进内存），失败后先看有没有残留进程再重试。
9. **拒答规则"生效"的方式是拒掉一条标错的题**——演示时问「StateBackend 是干什么的」
   被系统拒答，人工看觉得"材料里明明提到了它"。查 PG 原文，全文只有 3 处提到它，
   全是 `from deepagents.backends import StateBackend` 和 `backend = StateBackend()`，
   没有一句定义——这正好命中 prompt 规则 2(a) 里写的反例（"**import 语句**……一律拒答"）。
   真正错的是评估集：第 19 题 `StateBackend 这个类在文档里是干啥用的？` 被 LLM 从
   一个代码块出题、标成了"可答"，参考答案是从 `backend = StateBackend()` 反推的
   同义反复（"用来初始化 backend 实例的类"）。
   这是**第二次同类错误**（第一次是 `DeepAgents是什么`）：生成式出题会把"名字出现过"
   当成"文档里有定义"，而代码块是最容易出这种错的素材。代价很实际——不改判的话，
   RAGAS 会拿一个必然被拒答的题去算 answer_relevancy 和 context_recall，
   分数低得莫名其妙，还会被误读成"模型不行"。
10. **同一个 bug 会以两种面貌出现**——几小时后第三次改判：`LangChain 里提到的 RAG
   基础组件有哪些？` 标为可答，实际必须拒。原因是第 1 页原文写着
   `gives you primitives for RAG: custom retrieval tools, a , , , and .`
   —— 组件名是内联代码，被 pypdf 抽丢了，句子里只剩**四个空格和两个逗号**。
   坑 6 说的是"丢字导致误拒"，这里升级成"丢字导致标注错误"：
   出题时 LLM 看到的是同一份残句，它按自己对 RAG 的常识认为"这题有答案"，
   而系统运行时按材料判定"没有"。**标注和作答看的是同一份坏语料，
   却得出相反结论**——这类错误的排查方法只有一个：拿 PG 原文逐字核对答案所在位置。

11. **容器化之后，上传的文件会"消失"**——裸跑 uvicorn 时上传落在项目目录里，
    容器化后 `COPY . .` 把当时的 `app/data/uploads` 烤进了镜像层，
    运行时新传的文件只存在容器的可写层。`up -d --build` 重建容器，这些文件就没了。
    更隐蔽的是**它不报错**：PG 里 chunks 原文都在，问答照常工作，
    只有 `documents.file_path` 悄悄指向一个不存在的路径 —— 等到你想"改切分参数重新解析"
    那天才会发现源文件已经丢了。
    修法两条一起：`.dockerignore` 排掉 `app/data/uploads/`（顺带避免把用户 PDF
    固化进镜像层），compose 把这个目录 bind mount 进来。
    踩的时候还差点挂错位置：上传路径是 `Path(__file__).parents[2] / "data" / "uploads"`，
    在容器里展开成 `/app/app/data/uploads`——**多一层 `app`**，
    按直觉挂 `/app/data/uploads` 会静默失效（不报错，只是文件还是落在容器里）。

**一条方法论**：这三道错标全都有同一个指纹——**"参考答案"读起来像常识，不像原文**。
以后人工筛题就盯这一条：如果参考答案你能不看文档就写出来，那它大概率不是材料给的。

- [x] chunks 原文入 PostgreSQL（source of truth），Qdrant 只存向量+ID，可随时重建
      （`scripts/reindex.py`；纯向量模式的评估指标改造前后一字不差，说明回填链路正确）
- [x] 评估集从 10 题手写扩到 29 题（从真实 chunk 出题 + 本地质检 + 人工复核），
      并修掉 3 道标错的题（现为 17 可答 / 10 应拒 / 2 应通用答）
- [x] 新增生成层评估 `scripts/eval_boundary.py`：换模型后量"该答 / 该拒"这条线有没有移动，
      29 题 ≈ 5 万 token、3 分钟。换 qwen-plus 快照版时就是它抓到了漏拒和误拒各一道
- [x] 17 道可答题 × bge-m3 × 三模式 RAGAS 完整重跑（裁判 qwen-plus-2025-12-01，
      52 分钟、约 25 万 token）。结论：换多语言 embedding 后"混合检索跨语言 recall
      倒挂"消失（0.722→0.941），精排三项领先，见第三层表格
- [ ] 标准答案页只标了"出题块所在页"，同一答案在多页重复出现时会低估命中率
      （例：1000 字/200 重叠这组参数第 9 页和第 19 页都写了）。不按 top1 反推着改标注——
      那等于教模型做题，只能人工补标
- [x] Embedding 换 BGE-M3 对比（bge-small 跨语言弱：中文"智能体"查不到英文 "agent"）。
      结论：**换对了**。17 道可答题同一套切分下 hit@1 35%→59%（纯向量）、47%→71%（混合）、
      47%→59%（精排，差 2 题属噪声）；hit@5 59%→88%、82%→88%、88%→94%。
      已把正式集合切到 bge-m3（`reindex.py`，105 块 1.2 秒重建），
      代价是启动加载 22 秒、显存约 1.15GB（fp16）
- [x] 混合检索在跨语言语料上 context_recall 反而降（bge-small 时期 1.000→0.722）——
      已用 bge-m3 复核：**现象消失**（0.941 vs 0.941，精排 1.000）。
      BM25 那一路本身没变，是向量路把正确块重新顶回 top5，融合后不再被噪声挤掉
- [ ] 多文档隔离：无关文档会挤占 top5（实测塞进一份简历后，某题 recall 直接归零），
      需要按知识库/文档做过滤或分集合检索
- [ ] 300 字切分会把代码行切断，数值被截断：`chunk_size=1000, chunk_overlap=200`
      在索引里只剩 `chunk_overlap=2`（`00)` 整段丢失，下一块也没接上）。
      模型答"2"是照着材料答的，不是幻觉——但它相对 PDF 原文是错的。
      所以 `文本切分参数是多少` 不适合当演示题；要修得把 chunk_size 提到 500~800，
      或按结构切（代码块不切断），改完所有数字都要重跑
- [ ] **Qdrant 服务端 v1.12.4、客户端 1.20.0，差 8 个 minor**，启动会打一条
      `client version 1.20.0 is incompatible with server version 1.12.4` 的警告。
      实测检索和写入都正常（`reindex.py` 的建集合 / 删集合 / 灌 105 点全跑通，
      32.3 秒），警告来自客户端自带的版本检查，不是真实故障。
      但**不能原地升级服务端**——试过 v1.12.4 → v1.20.0 直接 panic 退出：
      `segment.json` 里的 `on_disk` 新版本只认 `mmap` / `in_ram_mmap`，
      中间版本改过存储布局且没留兼容迁移。要对齐版本只能删卷重建
      （原文在 PG，`reindex.py` 32 秒重建完）。Docker 化之前一直是本地 venv
      跑老客户端，所以这个不匹配是容器化才暴露出来的
- [x] 评估集扩充：`gen_evalset.py` 让 LLM 只看着单个 chunk 出题（手写题会"照着答案出题"，
      检索必中、分数虚高），本地向量检索免费质检，人工筛后固化 `eval/golden_set.json`；
      两个评估脚本统一读它，换题集不用改命令
- [ ] 拒答门槛仍靠经验值：正负例分数区间重叠（负例最高 0.661 > 正例最低 0.438），
      分数只做粗筛，真正判定靠 prompt；若要量化拒答质量，需要单独的拒答评估集
- [ ] 通用知识回答没有评估：标注了「以下不属于知识库内容」，但没有指标衡量
      它是否准确；也没接工具，实时信息（天气/股价）只能回答"无法获取"
- [ ] 多轮改写的鲁棒性没有量化：改写错一次，检索就偏一次（当前只在短句/含指代时才调，
      且改写失败自动退回原句）。真要评估需要多轮对话测试集
- [ ] 拒答边界的判定完全依赖 prompt：规则改一行，`什么是LangChain`（应拒）
      和 `文本切分器是什么`（应答）就可能同时翻转。现在靠"正例/反例对照"把两类分开，
      但这是提示词工程的固有脆弱性——更稳的做法是用一个小分类器或独立的可回答性判断
